# LLM 的成本结构与工程杠杆

> 这一节不尝试预测哪家公司赚不赚钱，而是回答一个对系统学习更重要的问题：训练和推理到底为什么贵，哪些技术决策会显著改变成本。

## 先看结论：成本不是一个数字，而是一组约束

大模型系统的成本，通常由下面几类因素共同决定：

- 训练计算
- 推理计算
- 数据处理与标注
- 集群网络、存储、电力和运维
- 工程团队本身的持续投入

其中最关键的不是记住一个总金额，而是理解哪些技术因素会把这些成本推高或压低。

## 训练为什么贵

训练成本高，通常来自下面几个方面：

### 1. 算力需求大

预训练本身就是海量矩阵运算。模型越大、训练 token 越多、实验次数越多，算力消耗就越高。

### 2. 不是只跑一次

真实研发不是“一把成功”。除了正式训练，还会有：
- 架构试验
- 超参数试验
- 失败作业重跑
- 评估和回归验证

因此，真正花掉的计算预算往往大于主训练作业本身。

### 3. 大规模训练强依赖基础设施

即使 GPU 本身是最大头，训练系统仍然离不开：
- 高带宽网络
- 高吞吐存储
- checkpoint 机制
- 集群调度和故障恢复

这些组件不一定像 GPU 那样最显眼，但会直接决定训练效率能否接近理想值。

## 推理为什么同样贵

推理和训练的不同点在于：训练更像阶段性的大作业，推理更像长期持续的线上服务。

推理成本通常取决于：

- 模型大小
- 输入和输出 token 长度
- 并发规模
- 延迟 SLA
- batch 策略
- 硬件利用率

如果请求量足够大，推理总成本完全可能接近甚至超过训练成本。原因很简单：训练作业会结束，在线推理不会结束。

## 采购方式也会改变成本结构

训练和推理算力一般有两种主要来源：

### 1. 自建或长期预留集群

特点：
- 前期资本投入高
- 单位算力成本可能更可控
- 需要自己承担机房、电力、运维和扩容复杂度

### 2. 云上租用或按需租用

特点：
- 前期资本压力小
- 资源获取更灵活
- 单位 GPU 小时成本通常更高
- 对可用性、排队时间和地域资源更敏感

注意这里的采购口径不能重复计算。比如如果按整机设备估算，就不要再把其中的 GPU 单独再加一遍。

## 一个更有用的推理成本心智模型

与其记某个“每百万 token 成本”的行业数字，不如先记住成本驱动关系：

$$
	ext{推理单位成本} \approx \frac{\text{GPU 小时成本}}{\text{单位时间内产出的有效 token 数}}
$$

这意味着，任何能提高有效吞吐或提高硬件利用率的技术，都会直接改善单位成本。

例如：
- 更高效的 batching
- 更好的 KV Cache 管理
- 更低比特量化
- 更适合场景的模型规模
- 更高效的推理引擎

## 为什么 decode 阶段尤其敏感

对自回归模型，prefill 和 decode 的成本特征不同：

- **Prefill** 更容易通过并行计算吃满算力
- **Decode** 每次只生成少量 token，更容易受到显存带宽、缓存管理和调度开销影响

这就是为什么很多推理优化章节都围绕 decode 展开，例如：
- KV Cache
- PagedAttention
- Continuous Batching
- Speculative Decoding
- Quantization

## 训练与推理分别受什么技术杠杆影响

| 成本项 | 主要驱动因素 | 典型工程杠杆 |
|-------|-------------|-------------|
| 训练计算 | 模型规模、token 数、并行效率、利用率 | 混合精度、并行策略、kernel 优化、通信优化 |
| 推理计算 | 模型规模、并发、延迟要求、吞吐 | 量化、KV Cache、batching、推理引擎 |
| 存储与 IO | 数据读取、checkpoint 频率、恢复时间 | 分片 checkpoint、异步写入、数据管线设计 |
| 集群效率 | 网络拓扑、调度策略、故障恢复 | NCCL 调优、拓扑感知调度、监控与自动恢复 |

## 为什么一些优化能带来真实业务价值

系统优化的价值不在于“论文里快了多少”，而在于能否改变下面这些结果：

- 同样的 GPU，训练更快结束
- 同样的硬件，服务更多请求
- 同样的 SLA，下更小的机器成本运行
- 同样的模型版本，更稳定地发布和回滚

所以：
- 训练吞吐提升，会缩短实验反馈周期
- 通信效率提升，会减少多卡扩展浪费
- 量化和调度优化，会直接降低线上单位 token 成本
- 更好的可观测性，会减少作业失败和排障成本

## 这一章真正想让你记住什么

不是“某家公司一年到底花多少钱”，而是下面几条：

1. 大模型系统的主要成本，本质上是算力成本和系统效率问题。
2. 训练和推理是不同的成本结构，优化手段也不同。
3. GPU 算力本身重要，但显存、带宽、通信、存储和调度往往决定最终效率。
4. 后续章节里的很多技术点，本质上都在回答同一个问题：如何让每一块 GPU 产出更多有效工作。

## 对后续章节的直接映射

| 成本压力 | 为什么会出现 | 去哪里学 |
|---------|-------------|---------|
| 算力不够用 | 矩阵计算量太大 | Ch02、Ch03、Ch05 |
| 多卡扩展效率差 | 通信和并行策略不理想 | Ch06、Ch08 |
| 单卡显存放不下 | 权重、激活、KV Cache 太大 | Ch05、Ch06、Ch07 |
| 在线推理太贵 | decode 吞吐低、利用率差 | Ch07 |

这就是为什么 GPU 系统工程不是“做底层优化的人”，而是直接影响训练速度、服务成本和产品交付节奏的人。
