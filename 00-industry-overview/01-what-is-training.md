# 模型训练到底在干什么

> 用工程师视角解释：所谓“训练模型”，本质上是在用数据和算力，把一组参数优化成一个可用的函数近似器。

## 核心类比

**传统软件开发**：人写规则，程序执行规则。

**模型训练**：人定义模型结构、目标函数和数据分布，让优化器自动把参数调到一个可用状态。

所以“训练”并不是让模型背答案，而是在大规模数据上反复做下面这件事：

```
1. 取一批样本
2. 用当前参数做预测
3. 计算预测和目标之间的误差
4. 反向传播误差，得到梯度
5. 用优化器更新参数
6. 重复很多次
```

最终产物不是一段显式规则，而是一组参数。这组参数决定了模型如何把输入映射成输出。

## 对语言模型来说，目标通常是什么

对当前主流自回归语言模型，最常见的预训练目标是：**根据前文预测下一个 token**。

```
输入: "今天天气"
目标: 预测下一个 token 更可能是 "很"、"不" 或其他内容

训练时:
  模型读入上下文
  输出下一个 token 的概率分布
  用正确答案修正参数
```

这个目标本身并不等于“会对话”或“会推理”。它更像是在逼着模型压缩语言、知识和模式统计规律。大量能力，尤其是语言理解、代码补全、模式迁移能力，往往是在这个过程中一起学到的。

## 从基座模型到可用产品

从工程上看，一个可用大模型通常会经历几类阶段，但具体配方因团队而异，不存在所有公司都严格一致的“四步标准流程”。

### 1. 预训练

- 数据：大规模文本、代码、文档等
- 目标：学习通用语言和知识分布
- 产出：基座模型
- 特征：通常有较强的补全能力，但不一定适合直接拿来做对话产品

预训练通常消耗绝大部分训练算力，也决定了模型能力上限、知识覆盖和基础表示能力。

### 2. 指令微调或监督微调

- 数据：指令-回答样本、多轮对话样本、任务样本
- 目标：让模型更好地遵循人类输入格式
- 产出：更像“助手”的模型

这一步通常不会重新定义模型的基础能力，但会显著改变输出风格、任务遵循性和可用性。

### 3. 偏好优化与安全对齐

- 数据：偏好对、排序标注、红队样本、安全策略样本
- 目标：让模型更符合偏好约束、产品约束和安全要求
- 常见方法：RLHF、DPO 及其变体

这一步更像是在“塑形”而不是“重建”。它会显著影响用户感知到的回答质量，但底层能力上限仍然强依赖预训练。

## 推理：训练结束后真正花钱的地方

训练完成后，得到的是一组参数文件。推理就是在用户请求到来时，用这些参数做前向计算。

对自回归大模型，推理通常可以分成两个阶段：

```
输入 prompt
    ↓
Prefill: 一次处理整段输入
    ↓
Decode: 逐个生成输出 token
```

典型情况下：
- **Prefill** 更偏计算密集，因为能在较长序列上并行做很多矩阵计算
- **Decode** 更容易受显存带宽、KV Cache 和调度效率影响，因为每次只生成很少的新 token

这里要注意，这是常见主导瓶颈，不是无条件真理。真实服务性能还会受 batch 大小、并发、模型结构、并行方式和系统实现影响。

## 为什么本地跑模型会感觉慢

以消费级 GPU 为例，你常见到的两个问题通常是：

- **显存不够**：模型权重、激活和 KV Cache 放不下
- **生成偏慢**：decode 阶段吞吐不高，系统常受显存带宽和访存模式约束

这正是后续很多系统优化存在的原因：
- 想让一张卡装得下更大模型，需要量化、切分或 offload
- 想让多张卡高效协作，需要模型并行和高效通信
- 想让在线服务更便宜，需要更好的 KV Cache 管理、批处理和推理引擎

## 训练 vs 推理：资源画像有什么不同

| 维度 | 训练 | 推理 |
|------|------|------|
| 目标 | 把参数训出来 | 用参数服务请求 |
| 运行模式 | 周期性的大规模作业 | 持续在线或离线服务 |
| 计算内容 | 前向 + 反向 + 参数更新 | 主要是前向 |
| 显存压力 | 参数、激活、梯度、优化器状态 | 参数、KV Cache、批处理缓存 |
| 常见系统难点 | 算力利用率、并行扩展、通信效率、checkpoint | 延迟、吞吐、带宽、显存利用率、调度 |

很多团队在训练上花大钱，也会在推理上持续花大钱。只要请求量足够大，推理总成本完全可能与训练同量级，甚至更高。这也是为什么推理优化已经不是边角问题，而是主线问题。
